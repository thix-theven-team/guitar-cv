Спецификация была написана как шаблон для разработки продукта и местами может отличаться от итогового результата.

## 0. Основные характеристики
Нынешняя версия (`v1`) подразумевает общий префикс `/api/v1` для всех эндпоинтов.
- Изменение версии (`v2`, `v3`) происходит только при значительных изменениях, обычные патчи/багфиксы не считаются.

Любой эндпоинт может выдать серверную ошибку во время выполнения работы, в таком случае он должен вернуть ответ следующего формата:
```json
// HTTP-код: 5xx в соответствии с конкретной ситуацией
{
	"status": "error",
	"error": {
		// описание ошибки, например INVALID_VIDEO_FORMAT
		// как именно описать ошибку - можно выбрать во время разработки
		"code": "",
		"message": string
	}
}
```

При ошибке со стороны клиента - например, использование неправильного HTTP-метода при вызове эндпоинта (`405 Method Not Allowed`) либо некорректные вводные данные (`400 Bad Request`) - эндпоинт возвращает ответ следующего формата:
```json
// HTTP-код: 4xx в соответствии с конкретной ситуацией
{
	"status": "error",
	"error": {
		"code": "",
		"message": string
	}
}
```

При возврате `fail`-ответа важно не отправлять sensitive данные в поле `error`, поэтому не стоит полностью вставлять туда стек вызовов. Можно обойтись общим описанием (например, "Формат данных не соответствует ожидаемому").

Система Rate Limit не предполагается для MVP и находится в бэклоге.

## 1. POST `/api/v1/submit`
Формат входных данных (`multipart/form-data`):

| Поле    | Тип          | Обязательно? | Описание                        |
| ------- | ------------ | ------------ | ------------------------------- |
| `video` | Файл (видео) | **Да**       | Видео, которое будет обработано |
Запрос проходит обязательную валидацию на формат файла.
1. Проверка MIME: если указанный MIME type не входит в список допустимых (например, список `video/mp4, video/webm, video/quicktime`, `video/...`), то эндпоинт выдаёт ошибку `415 Unsupported Media Type` и завершает выполнение.
2. Проверка через `FFprobe`: если `FFprobe` сообщает, что запрашиваемый файл не является видеофайлом, эндпоинт выдаёт ошибку `415 Unsupported Media Type` и завершает выполнение.
	- `FFprobe` входит в FFmpeg suite, который будет установлен на сервере. Поэтому для реализации можно, например, обойтись вызовом через `subprocess`:
```python
import shutil, tempfile

# video - загруженный файл, полученный как UploadFile
with tempfile.NamedTemporaryFile(suffix=".tmp") as temp:
	shutil.copyfileobj(video.file, temp)
	temp.flush()
	
	file_path = temp.name


# Пример проверки через ffprobe
import subprocess, json


# Может выкинуть subprocess.TimeoutExpired, в таком случае рекомендуется вернуть ошибку (см. пункт 0.1) со статусом 504
result = subprocess.run(
	["ffprobe", "-v", "error", "-show-streams", "-of", "json", file_path],
	capture_output=True,
	text=True,
	timeout=5
)
if result.returncode != 0: ... # Файл не является корректным видеофайлом - ошибка 415
	
# Может выкинуть JSONDecodeError, это ошибка 500
metadata = json.loads(result.stdout)

has_streams = any(
	stream.get("codec_type") == "video"
	and not stream.get("disposition", {}).get("attached_pic", 0)
	for stream in metadata.get("streams", [])
) # True, если в файле есть корректный видеопоток
```

Лимитация по размеру входного файла с ошибкой `413 Content Too Large` не реализована в MVP и отложена в бэклог как первый приоритет после сдачи MVP.

Если эндпоинт получает вызов любого метода кроме `POST`, он возвращает ошибку `405 Method Not Allowed`.

Обработка входного файла может происходить достаточно долго. Некоторые клиенты, даже некоторые веб-браузеры, полностью отклонят запрос ("превышено время ожидания"), если это будет происходить слишком долго. Поэтому API реализует двухэтапный процесс обработки файла. Данный эндпоинт (`submit-video`) возвращает случайно сгенерированный UUID и привязывает его к обработке, которая будет происходить после этого.
Формат выходных данных (`application/json`):
```json
{
	"conversion-id": string
}
```

При успешном исполнении, эндпоинт использует статус `200 OK`.

### 1.1. Подробнее о запуске процесса обработки
Реализация процесса обработки зависит от входных и выходных данных ML-части продукта.
Возможно, потребуется конвертация файла в один стандартизированный формат (например, на вход поступил `.avi`, он будет преобразован в `.mp4` через `subprocess` с ffmpeg), но так же возможно, что модель примет любой корректный видеофайл.
Выходные данные так же не приведены к стандартизированному формату и могут меняться.
Как итог, стоит пока что ориентироваться на mock-формат данных.

Во время реализации выходного mock-формата можно основываться на *нынешнем* формате моделей (может меняться):
```python
# Классификация
# (Ultralytics - raw JSON for backend):
[{"bbox_xyxy": [4.970125198364258, 77.91889953613281, 1628.0, 822.0], "confidence": 0.9413755536079407, "class_id": 1}] # {0: 'Acoustic_guitar', 1: 'Bass_guitar', 2: 'Electric_guitar'}
```
Модель YOLO так же выводит информацию о левой руке, но эта информация для бэкенда не является актуальной. В процессе реализации гомографии и работы с MediaPipe, будет предоставлен метод, который вернёт необходимую информацию для создания `.midi`-файла. Пример mock-формата выходных данных:
```python
temporal_notes: dict[float, list[Note]] = {
  0.0425, [Note(2, 3), Note(3, 5)], # 2 струна, 3 лад | 3 струна, 5 лад
  2.3181, [Note(3, 6), Note(4, 1), Note(4,3)]
}
```

Хранение продолжающегося процесса обработки можно выполнить, используя БД, например, SQLite:

| conversion_id | status     | created_at              | result_path                | error                   |
| ------------- | ---------- | ----------------------- | -------------------------- | ----------------------- |
| abc-123ef-... | processing | 2026-11-16 20:57:00.125 | `/results/output97452.mid` | NULL                    |
| def-456ab-... | failed     | 2026-11-16 20:15.00.372 | NULL                       | no guitar fret detected |


## 2. GET `/api/v1/conversions/<id>`
Эндпоинт проверяет, существует ли обработка с данным UUID. Если обработка не существует вообще, то эндпоинт выкидывает ошибку `400 Bad Request` и завершает исполнение. Иначе, эндпоинт возвращает следующий формат выходных данных (`application/json`) со статусом `202 Accepted`:
```json
{
	"status": 'processing' | 'ready' | 'failed'
}
```
Фронтенд может периодически вызывать этот эндпоинт, чтобы проверять статус обработки и, достигнув успеха, выдать пользователю файл.

## 3. GET `/api/v1/conversions/<id>/result`
Если `id` отсутствует либо не соответствует действительному процессу, эндпоинт выкидывает ошибку `404 Not Found` и завершает исполнение.
Если `id` соответствует процессу, который ещё не завершился, эндпоинт выкидывает ошибку `409 Conflict` и завершает исполнение.

Если `id` соответствует процессу со статусом `failed`, то формат выходных данных эндпоинта выглядит следующим образом (`application/json`, `200 OK`):
```json
{
	"conversion-id": string,
	"status": "failed",
	"error": {
		"message": // краткое описание
	}
}
```
Для этого потребуется хранить некоторую информацию о выполненных/выполняемых процессах обработки видео, чтобы точно указать проблему пользователю.

В случае успеха (`ready`), формат выходных данных эндпоинта (`audio/midi`):

| Поле     | Тип         | Описание                                       |
| -------- | ----------- | ---------------------------------------------- |
| `output` | `.mid`-файл | Результирующий файл после всех преобразований. |
Более формально можно описать следующим образом:
```
HTTP/1.1 200 OK
Content-Type: audio/midi
Content-Disposition: attachment; filename="output.mid"
```
При успешном исполнении, эндпоинт использует статус `200 OK`.

## 4. Постскриптум
Бэкенд ответственнен за очистку уже использованных файлов. Например, можно удалять обработанный контент через час после завершения обработки; если есть какие-либо метаданные от модели, их можно удалять через 2-3 часа.
